# О неторопливо обедающих философах

## Общий контекст

Классическая задача синхронизации — **Dining Philosophers Problem**, реализованная в разных архитектурных и технологических вариантах: от пошаговой симуляции до микросервисной и event-driven архитектуры.

---

## Описание задачи

### Условия

- 5 философов сидят за круглым столом
- Между каждой парой соседей лежит одна вилка (всего 5 вилок)
- Философ проводит время в размышлениях, но периодически ему нужно поесть
- Чтобы поесть, философу необходимы **обе вилки** — левая и правая
- После еды вилки возвращаются на стол

---

## Состояния философа

- **Thinking** — размышляет, не имеет вилок
- **Hungry** — проголодался, пытается взять обе вилки
- **Eating** — ест

---

## Состояния вилки

- **Available** — доступна
- **InUse** — используется философом или находится в процессе взятия/возврата

---

## Процесс симуляции

1. Философ становится голодным (`Hungry`) через случайное время
2. Для перехода в состояние `Eating` необходимо взять обе вилки
3. Процесс взятия вилок не мгновенный, вилки берутся по очереди
4. Порядок взятия вилок определяется стратегией
5. Философ может мгновенно положить уже взятую вилку
6. После еды философ возвращает вилки и переходит в состояние `Thinking`
7. Вилки возвращаются на стол мгновенно

---

## Отображение состояния

Пример вывода состояния симуляции в консоль:
===== ШАГ 150 =====

Философы:
Платон: Thinking (Action = ReleaseRightFork|ReleaseLeftFork), съедено: 22
Аристотель: Thinking, съедено: 233
Сократ: Eating (4 steps left), съедено: 33
Декарт: Thinking (3 steps left), съедено: 22
Кант: Hungry (Action = TakeRightFork|TakeLeftFork|ReleaseRightFork|ReleaseLeftFork|None), съедено: 33

Вилки:
Fork-1: Available
Fork-2: Available
Fork-3: InUse (используется Аристотель)
Fork-4: InUse (используется Сократ)
Fork-5: InUse (используется Декарт)


---

## Стратегия и координатор

> **Важно:**  
> Стратегия философа не должна знать состояние всех философов и всех вилок.  
> Допустима информация только о двух соседних вилках.

### Координатор

В некоторых задачах требуется координатор:

- знает состояние всех философов и всех вилок
- взаимодействие философа и координатора — событийное
- философ синхронно декларирует желание поесть
- координатор отправляет событие о возможности взять вилку

---

## Метрики

- **Пропускная способность** — количество съеденного за единицу времени
- **Время ожидания** — время нахождения философа в состоянии `Hungry`
- **Коэффициент утилизации вилок** — процент времени:
  - свободна
  - заблокирована
  - используется для еды

# Задача 1: ООП — пошаговая симуляция

## Описание

Реализовать консольное приложение с пошаговой симуляцией без многопоточности.  
Каждый шаг симуляции последовательно обрабатывает состояния всех философов.

## Требования

- Имена философов считываются из файла
- Симуляция длится **1 000 000 шагов**
- Контракты стратегии и координатора вынесены в отдельный проект
- Реализовать:
  - наивную стратегию без координатора
  - стратегию с координатором (через события C#)
- Определять deadlock (взаимную блокировку)

### Длительности состояний

- Размышления: 3–10 шагов (случайно)
- Еда: 4–5 шагов (случайно)
- Взятие вилки: 2 шага
- Освобождение вилок: мгновенно (обе одновременно)

### Метрики

- Пропускная способность — количество съеденного за 1000 шагов
- Время ожидания — в шагах
- В конце вывести:
  - **Score** (общее количество съеденного)
  - все метрики

# Задача 2: Многопоточная симуляция

## Описание

Консольное приложение с многопоточной симуляцией в реальном времени.  
Используется стратегия без координатора.

## Требования

- Каждый философ работает в отдельном потоке
- Длительность симуляции задаётся константой
- Отображение состояния каждые 100–200 мс

### Длительности состояний

- Размышления: 30–100 мс (случайно)
- Еда: 40–50 мс (случайно)
- Взятие вилки: 20 мс
- Освобождение вилок: мгновенно

### Метрики

- Пропускная способность (еда/мс)
- Среднее время ожидания философов (мс)
- Коэффициент утилизации вилок (%)

# Задача 3: Использование .NET Generic Host

## Описание

Реализовать консольное приложение с использованием **.NET Generic Host**, где каждый философ представлен отдельным `Hosted Service`.

## Требования

- Каждый философ реализован как `BackgroundService`
- Использовать Dependency Injection
- Конфигурация через `appsettings.json` и `IOptions`
- Использовать `IHostApplicationLifetime`
- Корректное завершение через `CancellationToken`

### Сервисы

- `PhilosopherHostedService`
- `IPhilosopherStrategy`
- Дополнительные сервисы: менеджер вилок, сборщик метрик и т.д.

### Пример Program.cs

```csharp
services.AddSingleton<ITableManager, TableManager>();
services.AddSingleton<IMetricsCollector, MetricsCollector>();
services.AddSingleton<IPhilosopherStrategy, LeftRightStrategy>();

services.AddHostedService(new Platoo(provider));
services.AddHostedService(new Aristotle(provider));
services.AddHostedService(new Socrates(provider));
services.AddHostedService(new Decartes(provider));
services.AddHostedService(new Kant(provider));

services.Configure<SimulationOptions>(
    configuration.GetSection("Simulation"));
```

- Корректный порядок взятия вилок для нативной стратегии

# Задача 6: Микросервисы

## Описание

Реализовать систему обедающих философов в виде микросервисной архитектуры, где каждый философ и стол являются отдельными HTTP-сервисами, взаимодействующими через REST API.  
Сохранение в базе данных не требуется.

## Архитектура

### Сервисы

- **Table Service (Стол)** — центральный сервис, управляющий состоянием вилок и сбором метрик
- **Philosopher Service** — отдельный экземпляр сервиса для каждого философа (всего 5 сервисов)

## Требования

### Технические требования

- Использовать **ASP.NET Core Web API** для всех сервисов
- Взаимодействие между сервисами только через **HTTP REST API**
- Каждый сервис развёрнут в отдельном Docker-контейнере
- Запуск всей системы осуществляется через **Docker Compose**
- Использовать **HttpClient** для межсервисного взаимодействия
- Необходимо разработать контракты взаимодействия между микросервисами

## Docker Compose

Необходимо создать файл `docker-compose.yml`, который запускает:

- 1 экземпляр **Table Service**
- 5 экземпляров **Philosopher Service** (по одному для каждого философа)

Каждый философ должен отработать заданное количество минут и сообщить столу о завершении работы.  
После завершения всех философов **Table Service** должен вывести итоговые метрики.

### Пример конфигурации

```yaml
services:
table-service:
  build: ./TableService
  ports:
    - "8080:8080"
  environment:
    - ASPNETCORE_URLS=http://+:8080
    - PHILOSOPHERS_COUNT=5
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
    interval: 30s
    timeout: 10s
    retries: 3

philosopher-plato:
  build: ./PhilosopherService
  environment:
    - ASPNETCORE_URLS=http://+:8081
    - PHILOSOPHER_NAME=Платон
    - PHILOSOPHER_ID=philosopher-1
    - LEFT_FORK_ID=1
    - RIGHT_FORK_ID=2
    - TABLE_SERVICE_URL=http://table-service:8080
    - SIMULATION_DURATION_MINUTES=5
  depends_on:
    table-service:
      condition: service_healthy
  ports:
    - "8081:8081"

philosopher-aristotle:
  ...
```

# Задача 7: Event-Driven микросервисы с координатором

## Описание

Реализовать продвинутую микросервисную систему обедающих философов с координатором, использующую гибридную архитектуру:

- **HTTP API** — для синхронных операций  
- **Асинхронные события** — для координации доступа к ресурсам  

Система должна использовать **MassTransit** или аналогичную библиотеку для обмена сообщениями, либо **RabbitMQ Client Library**.

---

## Архитектура

### Сервисы

- **Table Service**  
  Управляет состоянием вилок и обрабатывает HTTP-запросы от философов.

- **Philosopher Service**  
  Отдельный экземпляр сервиса для каждого философа (всего 5 сервисов).

- **Coordinator Service**  
  Координирует доступ философов к ресурсам (вилкам) с использованием событий.

- **Message Broker**  
  **RabbitMQ**, используется для обмена событиями между философами и координатором.

---

## Логика координации

Координатор должен реализовать **любую стратегию предотвращения deadlock**.

### Требования к взаимодействию

- Взаимодействие **философов и стола** должно быть **синхронным**  
  (через HTTP API)

- Взаимодействие **философов и координатора** должно быть **событийным**  
  с использованием:
  - MassTransit  
  - либо аналогичных библиотек  
  - либо нативного API RabbitMQ
